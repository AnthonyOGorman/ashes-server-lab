# Ashes client testing bridge

The bridge exposes fresh game observations, screenshots and bounded test controls to an LLM. Implementation and artifacts live here. The server chat owns `CPP/`; this bridge reads its telemetry with GET only. It does not author network packets, initialize characters, change server settings or launch/restart the game. Its MCP tools use only a resident input DLL; the separately invoked coordinated setup helper can explicitly attach the previously reviewed legacy adapter.

## Current verified capabilities

- Exact executable SHA256 and process lifetime validation, live GObjects pointer/index/serial checks, fresh local-controller possession and component links.
- Reflected pawn position, velocity, acceleration, movement mode, role, movement speed properties and time dilation. A non-atomic observation is explicitly labeled.
- `get_player_state` also reports the cached native `CurrentFloor`: walkable/blocking flags, floor distance, penetration flag, impact point/normal, and the hit component's live weak identity and outer chain. It verifies reflected struct sizes/field bounds and rereads the floor bytes to reject changes during sampling. Component/actor/level identities require valid weak serials; a Package without an allocated serial is explicitly labeled with pointer/index/class/name checks. An unavailable contact leaves other player telemetry usable. This observes an existing cached result and performs no floor trace or game call; contact at one location does not certify route coverage.
- Background PrintWindow screenshots without foreground or desktop cursor changes.
- Existing C++ server player/connection telemetry, labeled separately from native observations.
- Official MCP SDK stdio transport, seven named tools: `get_status`, `get_player_state`, `get_world_state`, `capture_screen`, `press_key`, `run_scenario`, `cancel_test`.
- Bounded WASD/space input through an already resident, reviewed input adapter. Legacy native protocol 1 and C++ protocol 2 are supported with pinned module paths, disk hashes and IPC build IDs in `vendor/input-adapters.json`. A changed C++ build refuses controls until its pinned contract is reviewed/refreshed. No new DLL is attached by these tools. Input requires both `--enable-input` and a matching, unexpired coordinated testing window in `session-access.json`.
- Scenario evidence includes screenshots, native before/after observations, server events, and explicit horizontal/vertical displacement assertions. Passing these assertions does not certify server/client prediction agreement, correct collision, walking causality or absence of rubberbanding.

Health, mana and stamina are currently reported as unmapped. The server developer is validating their runtime record identities. World StreamingLevels count is available; all-cell loaded/visible readiness is not claimed.

## Run from a normal desktop PowerShell

```powershell
& 'C:\Tools\Python310\python.exe' 'E:\Ashes Of Creation GPT\client-testing\cli.py' --tool get_player_state
& 'C:\Tools\Python310\python.exe' 'E:\Ashes Of Creation GPT\client-testing\cli.py' --tool get_world_state
& 'C:\Tools\Python310\python.exe' 'E:\Ashes Of Creation GPT\client-testing\cli.py' --tool capture_screen
```

`Start-Observe.ps1` runs the first command. The bridge uses an inspection only to obtain candidate LocalPlayer addresses and its process identity. It rereads values and validates current pointer/index/serial identities. `Refresh-Observe.ps1` runs the existing C++ read-only inspector and saves a private `binding.json` here, without modifying server files. The bridge prefers that private binding, otherwise uses the server's existing inspection. After a new game process, run `Refresh-Observe.ps1`; the bridge refuses a seed from another process lifetime. Start a fresh MCP process when the game lifetime changes. A restricted agent sandbox can deny Windows module enumeration even when read-only access is requested; use the normal desktop shell.

Artifacts are written under `runs/`. No model provider or API key is needed to run the bridge.

## MCP connection

`ashes-client-testing` is registered in the user's global Codex MCP configuration in observation mode. Existing active chat tool catalogs may require a later MCP reload or new chat connection to expose it; the CLI works immediately. Registration does not restart Codex, the game or the server.

`codex-mcp.example.toml` contains the registration stanza, and `mcp-config.example.json` is available for other MCP clients. The registered command is:

```text
C:\Tools\Python310\python.exe E:\Ashes Of Creation GPT\client-testing\cli.py --mode mcp
```

For input testing, coordinate with the server chat first. The window file must contain mode `client-testing-exclusive`, `coordinated_window: true`, this chat's owner ID, the exact PID/creation FILETIME, and `expires_at` no more than 15 minutes ahead. New windows also specify `allowed_actions`: `adapter-setup`, `ui-entry`, and/or `movement`. Each helper verifies its action scope before accessing the input driver, so an entry-only window refuses movement. Older leases without that field retain their original behavior. Start a dedicated CLI/MCP process with `--enable-input` during that window. Each key step rechecks the window. Closing or cancelling a request releases held keys; the adapter's existing watchdog provides additional IPC-loss cleanup. Shift, walk/run toggle and clicks are deliberately not exposed by this first bridge version.

## UE4SS trial

Official experimental asset `UE4SS_v3.0.1-1161-g6eb3d9bc.zip` is pinned to SHA256 `938dc9901e6452cad3120280681c93a00ae12df2b259668815a150e221a35563`. Release metadata is recorded in `vendor/release-manifest.json`; extracted file hashes are in `vendor/stage-manifest.json`. The stable `v3.0.1` release dates to 2024 and was not selected as a compatibility assumption for this UE5.6 client.

`stage_ue4ss.py` validates the pinned archive, rejects unsafe members and prepares `vendor/trial-package/`. All bundled mods and the optional AshesObserve mod are disabled. Console/cheat-manager enablers and hot reload stay disabled. UE4SS itself installs native hooks if loaded, so a baseline startup trial is required even with mods disabled.

`install_ue4ss.py install` requires an explicit coordinated UE4SS install window (`allow_ue4ss_install: true`) and no running Ashes client. It refuses an existing `dwmapi.dll` or `ue4ss/` directory, validates every source hash and records exact installed file identities. `uninstall` verifies all recorded hashes before removing only recorded files and empty directories; new logs/caches are preserved. Do not run these while the server chat owns the session. Neither installer command has been run against the real game yet.

After the all-mods-disabled startup trial passes, the optional `ue4ss/AshesObserve/Scripts/main.lua` can be enabled for a separate trial. It samples fixed reflected properties once per second, schedules reads on the game thread and never sends RPCs or writes game properties. It is not live-validated yet. A `ue4ss/STOP` file stops its loop. Its output is diagnostic material until correlated with the bridge's independent native process/object checks.
